# Dataset

The project uses locally available DCASE 2025 Task 5 Part 1 source material.

## Sources

- Extracted audio source outside the project: `dcase_25_task5_audio_part_1`.
- Metadata source outside the project: `dcase_2025_qa/dcase_2025_question_path`.
- Original ZIP source archive remains outside the project and was not modified.

## Discovered Audio Structure

The extracted audio directory contains flat split directories:

- `train/*.wav`
- `dev/*.wav`
- `__MACOSX/` archive metadata directory

Excluding `__MACOSX`, the copied project dataset contains 4,443 WAV files:

- 1,778 train WAV files
- 2,665 dev WAV files

## Discovered Metadata Structure

The metadata source contains one JSON file per QA record, with fields:
`question`, `choice`, `answer`, `id`, `audio_url`, `question_type`.

The metadata source contains 8,221 train JSON files and 2,466 dev JSON files.
Of the train JSON files, 1,778 resolve to the available local Part 1 train
audio. All 2,466 dev JSON files resolve to available local dev audio.

## Reproducible Manifest Generation

`dataset/dcase_part1/splits/{train,validation,test}.jsonl` are generated by
**`scripts/build_manifests.py`**, run from raw metadata -- they are not a
manually-produced snapshot. Re-running the script from the same raw metadata
reproduces the same manifests. Pipeline:

1. Discover and normalize every raw metadata record
   (`src/data/preprocessing.py:normalize_raw_record`).
2. Keep only records whose referenced audio file exists locally.
3. `dev` records become the `test` split verbatim -- the official DCASE dev
   partition is kept intact as the held-out evaluation set and is never
   modified by remediation.
4. `train` records are split at the **audio level**: sorted by `audio_id`,
   every 10th unique audio_id is assigned to `validation`, the rest to
   `train` (the `official_train_audio_level_90_10_validation_official_dev_as_test`
   policy named in `configs/dataset.yaml`).
5. **Leakage remediation** (see below): any audio_id in the train/validation
   pool that also appears in `test` is removed from train/validation. `test`
   is never altered.
6. Validate: zero missing audio, zero duplicate record_ids, zero remaining
   cross-split audio_id overlap (enforced -- the script raises if this
   invariant doesn't hold).
7. Write the three manifests. Any manifests already present are backed up
   under `dataset/dcase_part1/splits/_backup_<timestamp>/` first.

Run it with `python scripts/build_manifests.py` (add `--dry-run` to preview
without writing).

## Audio-Level Data Leakage: Detection and Remediation

Leakage detection compares `audio_id` (the underlying-recording identifier
from the raw metadata's `id` field), not local file *paths* -- paths cannot
collide across splits by construction (train audio lives under
`audio/train/`, dev audio under `audio/dev/`), so a path-based check alone
would miss genuine content duplication. Comparing `audio_id` and then
verifying file *content* (SHA-1 hash) revealed that the same recording
appears in both the source train pool and the official dev/test partition:

- **184 audio_ids** were found in both the train+validation pool and test
  (164 that would have landed in `train`, 20 in `validation`, under the
  current audio-level split assignment).
- Content hashing confirmed these are byte-identical files, not a
  coincidental id collision (the id scheme -- 10-character alphanumeric
  strings such as `us1RbA4r9t` -- is consistent with AudioSet/YouTube-derived
  clip ids, which the DCASE Part 1 train and dev partitions apparently draw
  from a shared underlying pool with some overlap).
- Of those, several had the *exact same question* asked on both sides
  (literal (audio, question, answer) duplication), and the rest had a
  *different* question on the same audio (the model would still have seen
  that exact recording during training).

**Remediation applied**: the official dev partition is kept intact as
`test` (2,466 records, 2,415 unique audio, unchanged). All 184 overlapping
audio_ids -- and every QA record attached to them -- were removed from
`train` and `validation`. Post-remediation counts:

| Split | Before remediation | After remediation |
|---|---|---|
| train | 1,600 records / 1,600 unique audio | 1,436 records / 1,436 unique audio |
| validation | 178 records / 178 unique audio | 158 records / 158 unique audio |
| test | 2,466 records / 2,415 unique audio | 2,466 records / 2,415 unique audio (unchanged) |

Final invariant (enforced by `scripts/build_manifests.py` and checked by
`scripts/validate_splits.py`): `train ∩ test = ∅`, `validation ∩ test = ∅`,
`train ∩ validation = ∅` at the audio_id level.

The audio-level train/validation assignment and the leakage remediation
above are both produced deterministically by `scripts/build_manifests.py`
from the raw metadata, making the prepared manifests fully reproducible
from source.

## Test Set: Multiple Questions Per Clip

The test set has 2,466 QA records over 2,415 unique audio files -- 51 audio
clips have more than one question attached. This is an accepted property of
the official DCASE dev partition (kept intact) and is not itself leakage: no
answer to one question on a clip discloses the answer to another question
about the same clip in general, though question-type-specific correlation
(e.g. two "sound counting" questions about the same recording) is possible
and is a caveat for interpreting per-clip error analysis, not a validity
blocker.

## Audio Integrity: MPEG/MP3 Data Saved as `.wav`

`scripts/validate_audio_integrity.py` checks every manifest-referenced audio
file with the actual runtime audio stack (`soundfile`/`librosa`), not
Python's stdlib `wave` module (which only understands plain integer-PCM RIFF
and misreports both valid float-PCM WAV and MP3-in-.wav files as
"corrupted"). Result, checked against all 4,009 unique manifest-referenced
files after remediation:

- **All 4,009 files decode successfully** with `soundfile==0.12.1`
  (bundled `libsndfile 1.2.0`, which added native MP3 decoding).
- **801 of the 2,466 test-split records (~32.5%)** reference audio whose
  magic bytes are MPEG/MP3 (`audio/dev/*.wav`), not real WAV containers --
  698 with an MPEG frame-sync header, 103 with an `ID3` tag. This is
  entirely isolated to the test/dev-sourced audio; zero occurrences in
  train or validation.
- **These files are NOT transcoded.** They decode correctly with the pinned
  audio stack, so transcoding would only add risk (re-encoding artifacts,
  a second on-disk copy to keep in sync) for no correctness benefit.
  `requirements.txt` pins `soundfile==0.12.1` specifically because of this;
  an older `soundfile`/`libsndfile` build (pre-1.2.0) would fail to decode
  these files, so this pin is load-bearing, not incidental.

Run `python scripts/validate_audio_integrity.py` to re-verify; it exits
non-zero if any manifest-referenced file fails to decode.

## Answer / Choice Consistency

`scripts/validate_splits.py` checks whether `answer` appears verbatim among
`choices` (`src/data/validation.py:answer_choice_consistency`). In the
current test manifest, 13 records fail a raw string check. Stripping
trailing punctuation before comparing (choice lists have a stray trailing
comma the `answer` field lacks) automatically resolves **8** of them
(`dev_aqa_1106`, `141`, `164`, `168`, `170`, `175`, `181`, `320` -- e.g.
choice `"C. He is cooking in a kitchen,"` vs answer `"C. He is cooking in a
kitchen"`); the evaluation-time matcher
(`src/evaluation/metrics.py:normalize_answer`) already strips
non-alphanumeric characters and was never affected by this artifact.

**5 records remain genuinely malformed** in the source metadata after
normalization and are **not** auto-corrected or deleted:

- `dev_aqa_1152` (answer `"D. (B)(A)(C)"`) and `dev_aqa_1169` (answer
  `"C. (B)(A)(D)"`) have answers that are an ordering of option letters,
  not a single selected choice -- these look like a temporal-ordering
  question type whose answer schema doesn't fit the single-choice A/B/C/D
  format used everywhere else.
- `dev_aqa_1565` has an answer (`"B. Focused and industrious turning
  abruptly dangerous or negative"`) that appears to blend the text of two
  different choices (B and C) -- a corrupted/concatenated ground truth.
- `dev_aqa_149` and `dev_aqa_614` have a genuine **letter/text
  misalignment**: for `dev_aqa_614` the answer field is `"B. A countryside
  railway"`, but that text actually belongs to choice C (`choices[1]` =
  "B. A busy city street"); for `dev_aqa_149` the answer is `"A. He is
  discussing a controversial topic"`, but that text belongs to choice C
  (`choices[0]` = "A. He is arguing with someone nearby,"). A model that
  correctly identifies the audio and answers with the *correctly-lettered*
  choice would be scored as **incorrect** under both the raw and
  option-label matchers, purely because of this source defect.

**Recommendation**: report test accuracy both including and excluding these
5 record_ids, or exclude them from headline metrics with a footnote. They
are left in the manifest (not deleted) so the discrepancy remains auditable;
`results/metrics/data_split_validation.json` records them under
`answer_choice_consistency.genuinely_malformed_examples` for every future
validation run.

## Question Types

Test includes one question_type (`audio detection`, 2 records) not present
in train/validation (`sound detection` is the closely related, much larger
category) -- reported by `scripts/validate_splits.py`'s
`question_types_missing_from_train`, not remediated (too small a category to
usefully rebalance, and it is a legitimate part of the official dev set).
